# Real Estate Comments: development notes

How the project is structured and why, for anyone working on it, including AI coding assistants used for routine tasks. Read this before changing anything. Most of the non-obvious constraints come from data that's already in production and from how the two property sites behave, not from the code.

**Keep this file up to date.** When you change behaviour, architecture, data, commands or conventions described here, update this file in the same change.

**Rebuild after changes.** After changing anything that ends up in the extension (`src/`, `icons/`, `package.json` version, build script), run `pnpm build`, even for small changes, so `dist/chrome` and `dist/firefox` stay current and the loaded extension can be reloaded and tested straight away (see "Loading locally"). Don't leave `dist` stale after a failed build.

**Git is handled by the maintainer.** Assistants and other tools shouldn't commit, push, or create branches, tags or releases: leave changes uncommitted in the working tree, with a summary of what changed.

## What the extension does

A browser extension that adds a comment section to property pages on **realestate.com.au** and **domain.com.au**, so renters and buyers can share what a property is really like. Users can read, post, upvote and delete their own comments. Off property pages, the panel shows the most recent comments across all properties.

It ships for **Chrome** and **Firefox**, both **Manifest V3**, from one codebase. Published on the Chrome Web Store and Firefox Add-ons (links in README.md). Comments are stored in **Firebase** (Firestore, project `realestatecomments`) with anonymous auth.

2.0 was a full rewrite of 1.x (plain JS, webpack, page-global CSS) in TypeScript and Preact. Comments saved by 1.x must keep working; see "Data model".

## Architecture

```
property page                                           background (service worker / event page)
─────────────────────────────────────────────           ─────────────────────────────────────────
content/index.tsx
  watchPage(): URL poll + <title> observer
  → resolvePageState(url, title)  [page-state.ts]
     → identifyProperty()          [shared/property.ts]
  → App (Preact, in a shadow root)
     useComments(property.input)
       callBackground('listComments', {property}) ───►  router checks sender + isPropertyInput()
                                                        buildPropertyKeys() → Firestore `in` query
                            ◄── {ok, data: CommentView[]} | {ok: false, error}
     Composer → 'createComment'  ─────────────────────►  validate → rate limit → ban check → addDoc
     Comment → 'toggleVote' / 'deleteComment'  ───────►  transaction / ownership check
     'setBadge' (comment count) ──────────────────────►  action.setBadgeText for that tab
                            ◄── 'togglePanel'            toolbar button / Alt+Shift+C
```

- **Background owns Firebase.** One signed-in session, the page can't tamper with it, and the content script never sees other users' IDs: `CommentView` only has `isOwn` and `hasVoted`.
- **Messages:** every request is `{ type, ...payload }` from `BackgroundApi`; every response is `Result<T>` (`{ ok: true, data }` or `{ ok: false, error }`, where `error` is a user-facing message). The background listener uses `sendResponse` + `return true` because Chrome doesn't accept a returned promise. To add a request: add it to `BackgroundApi`, add a handler in `background/index.ts` (the `Handlers` type forces it), validate its payload there.
- **Errors shown to users:** throw `UserError` in the background for messages that are safe to show; Firebase errors are mapped in `userMessage()`; anything else becomes a generic message (full error in the background console). In the content script, `callBackground` throws `ExtensionError` with that message; "Extension context invalidated" becomes "refresh the page".
- **UI isolation:** the UI is a `<real-estate-comments>` element with an open shadow root, appended to `<html>`. `styles.css` is bundled as text and injected into the shadow root, so site CSS can't break it and it can't affect the site. Use `px`, not `rem`, in the CSS (rem follows the site's root font size).
- **Site access:** Firefox lets users switch a Manifest V3 extension's site access off (it's an optional permission there; installs normally grant it), and Chrome has "on click" access. Without it the content script never runs, so the toolbar button checks: if access isn't known to be granted, it calls `permissions.request` for `SITE_MATCHES` straight away (it must happen inside the click, or Firefox refuses; if access is already granted it resolves without a prompt), then opens the panel, reloading the tab with `panelOpen` set if the content script wasn't there. No new permission is needed. Not covered by automated tests: check by hand in Firefox (about:addons → the extension → Permissions → switch the sites off, then click the toolbar button on a listing).
- **Orphaned content scripts:** after the extension is updated or reloaded, the old content script loses `ext.runtime.id`; the watcher notices and removes its UI. A newly injected copy also removes any existing host element.
- **Firebase in MV3:** use `firebase/firestore/lite` (REST over fetch; full Firestore uses WebChannel/XHR, which doesn't exist in a service worker) and `firebase/auth/web-extension` (the default build pulls in DOM/popup code). Don't switch to the full SDK entry points.

## Identifying the property (`shared/property.ts`)

This is where 1.x was unreliable, so be careful here.

**The goal: one comment thread per physical property**, whichever page it's left on: rent, sale or sold listing, a re-listing with a new ID, a property profile, on either site. Everything below serves that. `tests/property.test.ts` → "one property, every page" holds real URL/title sets for the same property across all of its pages; any change here must keep them producing one key.

**Page types and URL formats** (`parsePropertyUrl`), checked on the live sites in October 2026:

| Site              | Page               | URL                                                                                                 |
| ----------------- | ------------------ | --------------------------------------------------------------------------------------------------- |
| realestate.com.au | rent/sale listing  | `/property-house-nsw-epping-441106232`                                                              |
| realestate.com.au | sold listing       | `/sold/property-house-nsw-epping-152308708`                                                         |
| realestate.com.au | property profile   | `/property/46-stanley-rd-epping-nsw-2121/`, `/property/unit-41-10-14-hazlewood-pl-epping-nsw-2121/` |
| realestate.com.au | off-market listing | listing URL, unchanged (a 404 page: "Looks like this page is off the market")                       |
| domain.com.au     | rent/sale listing  | `/2-5-chester-street-epping-nsw-2121-18359019`                                                      |
| domain.com.au     | sold listing       | same URL as the listing                                                                             |
| domain.com.au     | property profile   | `/property-profile/46-stanley-road-epping-nsw-2121`                                                 |
| domain.com.au     | expired listing    | redirects to the suburb's search page                                                               |

**Titles** (`parseAddressFromTitle`), same pages in the same order:

- realestate.com.au rent/sale: `72 Somerset St, Epping, NSW 2121 - House for Rent - realestate.com.au`
- realestate.com.au sold: `46 Stanley Road, Epping, NSW 2121 - Property Details`
- realestate.com.au profile: `46 Stanley Road, Epping, NSW 2121 - realestate.com.au`
- realestate.com.au off-market: `Real Estate, Property & Homes For Sale - realestate.com.au` (no address)
- domain.com.au rent/sale: `2/5 Chester Street, Epping NSW 2121 - Apartment For Rent | Domain`, or `3 Helen Street, Epping NSW 2121 | Domain`
- domain.com.au sold: `Sold 46 Stanley Road, Epping NSW 2121 on 10 Oct 2026 - 2021146795 | Domain`
- domain.com.au profile: `46 Stanley Road, Epping | Property Value Estimate & History | Domain` (no state/postcode; taken from the URL)

realestate.com.au listing URLs only carry state and suburb; every other format carries the address slug, state and postcode. Anything else on those sites is a "browse" page (no property). Suburb search results pages are browse pages too, with an `area` taken from the URL (`parseAreaUrl`; see "Suburb stats on search pages").

How a property's pages relate (why the key must come from the address, never a listing ID):

- **realestate.com.au deletes a listing's page when it's sold or leased** and creates a sold listing with a **new ID** under `/sold/`. Old IDs 404 at both `/property-…` and `/sold/property-…`, with no address anywhere on the page, so there's nothing to show there.
- **domain.com.au keeps the listing URL when it sells** but changes the title to "Sold … on <date> - <id>". The "Sold" prefix is stripped (`STATUS_PREFIX`). 1.x didn't strip it, so it may have saved sold-page comments under "sold <address>"; that form is still looked up (`PropertyInput.titleAddress`).
- **Spellings differ between pages of the same site**: realestate.com.au listing "72 Somerset St", profile "72 Somerset Street", profile URL "46-stanley-rd". Normalization (see Data model) gives them one key.
- **Comments cross sites**: comments posted through realestate.com.au show on domain.com.au's pages for the property and vice versa (verified with real comments).

Other things the live sites showed:

- **Both sites navigate client-side** from search results to listings. The URL changes first and the title follows (realestate.com.au ~70 ms, domain.com.au ~560 ms). Search-page titles mention the suburb ("Rental Properties and Real Estate in Epping, NSW 2121") but have no street number, so they're rejected.
- **`og:title` isn't updated** on client-side navigation (domain.com.au keeps the search page's), so don't use it. The `<h1>` holds the address on every page type and could be a fallback if titles change. realestate.com.au pages also have schema.org `Residence` JSON-LD with a `PostalAddress` (not used; unknown whether it updates on client-side navigation).
- Neither site links listings directly to each other, so listing-to-listing navigation only happens through search results or history.

The street address is everything before the suburb, so it may contain commas (`Unit 5, 12 Smith St`). **The title is read from the `<title>` element's `textContent`, not `document.title`**, because `document.title` collapses whitespace and 1.x saved keys with the raw spacing (e.g. `97  yates ave`).

**Checking the title against the URL** (`matchAddressToUrl`) is what prevents comments being shown or saved for the wrong property. Both sites navigate client-side in places, and the URL can change before the title does, so a title is only trusted when it agrees with the URL:

- `full`: the URL contains the street address and it matches (compared via `comparableAddress`, so `unit-41-10-14-hazlewood-pl` matches "41/10-14 Hazlewood Place"). Trusted immediately. Unexpected words before the address in the title are trimmed off using the URL as the guide.
- `partial`: only suburb/state/postcode could be checked (realestate.com.au listings). Trusted on first page load, or after an in-page navigation once the title has changed or has been stable for `SETTLE_MS`.
- `none`: contradicts the URL. Keep waiting; after `GIVE_UP_MS` show "Couldn't identify this property".
  Once a page's property is resolved it sticks until the URL path changes. Query strings and hashes are ignored (`pageKey`), since galleries and maps change them.

Listings that hide the address ("Address available on request") have no street number and are rejected. Otherwise they'd all share one key per suburb. **Known limitation:** some listings give only the building address without the unit ("22-28 Cambridge Street"), so all units advertised that way share one thread. Nothing on the page identifies the unit.

### Checking the live sites

Both sites block automation. curl and WebFetch get 403/429, and so does any browser that has a debugger attached while the page loads (Playwright, `connectOverCDP`) or has `navigator.webdriver` set.

**`pnpm live-check`** (after `pnpm build`) gets through by avoiding those two signals:

- It starts the installed Chrome over `--remote-debugging-pipe` with a temporary profile and `--disable-blink-features=AutomationControlled`.
- It loads `dist/chrome` with the `Extensions.loadUnpacked` CDP command.
- It opens tabs without attaching, and attaches only after the page has loaded, to read the page and the extension's panel.

By default it follows two listings from each site's Epping NSW rental and sold searches; pass URLs to check specific pages. It's read-only (it opens the panel but never posts), and it fails if the panel's address doesn't match what `identifyProperty` expects. A Chrome window opens while it runs. Keep the volume to a handful of pages.

When a site changes its titles, run `pnpm live-check`, add the new format to `parseAddressFromTitle`, and add cases to the "live site titles" and "one property, every page" tests in `tests/property.test.ts`. Prefer adding over replacing, since old formats may still be served.

## Data model (Firestore) — compatibility rules

Collection **`listingcomments`**. One document per comment:

| Field                   | Notes                                                                                                                                |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| `address`               | Lowercase street address. **The lookup key**, with `suburb`.                                                                         |
| `suburb`                | Lowercase, single-spaced.                                                                                                            |
| `state`, `postcode`     | Lowercase state code, 4-digit postcode. Not part of the query (no index); used to filter results client-side.                        |
| `url`                   | Page URL without query string.                                                                                                       |
| `text`, `username`      | Comment markdown (5–1200 chars, ≤ 50 lines); name (≤ 50 chars, default `Anonymous`).                                                 |
| `uid`                   | The poster's **anonymous extension user ID** (see below), not the Firebase Auth UID.                                                 |
| `authorAuthUid`         | The poster's **Firebase Auth UID**, which the rules check on delete. Missing on comments from 2.0.0 and 1.x.                         |
| `createdAt`             | Timestamp (`serverTimestamp()` from 2.0; client `Date` in 1.x). Sort key.                                                            |
| `timestamp`             | ISO string from the client. Legacy; still written.                                                                                   |
| `votes`, `userVotes`    | Upvote count and `{ [userId]: 'up' }`. Added on first vote.                                                                          |
| `editedAt`              | Timestamp of the last edit (server time). Only on edited comments (from the release after 2.0.0).                                    |
| `parentId`, `replyToId` | Replies only: the top-level comment it's under, and the comment it answers (the parent or another reply). See "Replies and editing". |

Collection **`bannedUsers`**: documents with a `uid` field. A match blocks posting and voting ("error 90001"). Bans added by `pnpm moderate` also have `bannedAt` and `commentId`, for reference.

Collection **`reports`** (from the release after 2.0.0): one document per report, ID `<commentId>_<reporter's Auth UID>`, with `commentId`, `reason` (an ID from `REPORT_REASONS`), `details` (≤ 1000 chars, may be empty), `reporterAuthUid` and `createdAt` (server time). `pnpm moderate` adds `status` (`removed` or `dismissed`; none means open) and `resolvedAt`. Reports are kept after they're resolved, as a record of how complaints were handled. The comment's text isn't copied into the report.

**Rules for changing any of this:**

- **Don't add, rename or remove fields** without updating the **security rules** first (`firestore.rules`, see "Security model"). They reject unknown fields on create (`hasOnly`) and any update other than a vote, so a new field would break posting for everyone.
- **Queries must be served by existing indexes.** The comment lookup is `address in [...] AND suburb == x ORDER BY createdAt DESC LIMIT 100`, which uses 1.x's composite index (address, suburb, createdAt). The recent list is `ORDER BY createdAt DESC LIMIT 10`. A query needing a new composite index fails until it's created in the console.
- **Address keys:** new comments are saved under `canonicalAddress()` (lowercase, single spaces, `unit 5, 12 x` → `5/12 x`, street type spelled out: `st` → `street`). Lookups query every spelling in `buildPropertyKeys().addressVariants`: canonical, abbreviated street type, and the **1.x key** (`legacyAddress()`: title text lowercased, `" - "` → `"-"`). That's how a house listed as "97 Yates Ave" on one site and "97 Yates Avenue" on the other shares comments, and how 1.x comments are still found. Never drop the legacy variant. Audit on 2026-10-11 (19 comments): all stored addresses are canonical. The one exception, document `EOrAimxFhGiyEyKGv6Dm` (`97  yates ave`, double space, from a sloppy 1.x title), was fixed by hand in the console; property pages other than its original listing couldn't find it, because no variant can guess stray whitespace. If old data like that turns up again, fix the record rather than adding variants. Keep the variant list ≤ 30 (Firestore's `in` limit). `tests/property.test.ts` has real stored keys; keep those tests passing.

## Caching (`background/cache.ts`)

Every Firestore read goes through `cached(key, ttl, load, fresh)`, so page views, tab switches and search keystrokes don't repeat the same queries. The biggest saving is listing pages: the panel loads the property's comments on every listing view (for the launcher's count), most properties have none, and those empty results are cached too.

- **Where:** `storage.session`. It's shared by all tabs, survives Chrome stopping the background service worker (in-memory caches were lost after ~30 s idle), is cleared when the browser closes, and is never written to disk. It falls back to memory if `storage.session` fails. Expired entries are pruned every 50 writes; on a quota error the cache is cleared.
- **TTLs** (`TTL` in `background/comments.ts`): property comments, Recent and search lookups 5 min; the search's 500-comment scan and suburb stats 10 min; the ban check 60 min. New comments are rare, so other people's comments can take up to 5 minutes to appear.
- **Own writes are instant:** posting, voting and deleting call `invalidate('property:', 'recent', 'search:')`. A read that was already fetching when the write happened isn't cached (a generation counter), so it can't put stale data back.
- **Refresh:** the ↻ button on the property tab and the Recent tab sends `fresh: true`, which fetches again, but **at most once per `MIN_REFRESH_INTERVAL` (30 s) per key**: a refresh sooner after the last fetch is answered from the cache, whichever tab it comes from, so spamming refresh can't hammer the database. The button also rests for 2 s after each click, and spins for at least 0.6 s so an instant cached answer still gives feedback.
- **Deduplication:** concurrent requests for the same key (e.g. two tabs on one listing) share one fetch.

`pnpm e2e` checks this against the real extension by counting the background's Firestore queries: revisiting a property sends none, and repeated refreshes straight after a fetch send none (`tests/cache.test.ts` covers refreshing after the interval). Keep new reads going through `cached()`.

## Sorting and filtering (`views.ts`)

Comment lists (the property tab, and a property opened from Search or the Watchlist) have an always-visible dropdown (`ViewSelect`, a styled native `<select>`): **Newest**, **Top**, or **With photos** (threads where the comment or a reply links an image shown as a thumbnail, newest first). Newest and Top are remembered (`sort`); With photos is a filter for the current panel only, and posting a new comment switches back to Newest. With nothing to show, a notice offers "Show all comments". Search results have their own dropdown: **Best match** (the default ranking), **Newest**, **Most comments**, **With photos**.

## Suburb stats on search pages (`parseAreaUrl`, `areaStats`)

On a suburb's search results page, the Recent tab starts with a card (`AreaCard`): the suburb, how many comments and properties it has, and **See them**, which searches for the suburb and postcode (e.g. "Concord 2137", which the search's suburb and postcode lookups find). With no comments it says so.

- **Which pages** (`parseAreaUrl` in `shared/property.ts`, tested): realestate.com.au `/rent|buy|sold|leased/in-<suburb>,+<state>+<postcode>/…` and domain.com.au `/rent|sale|sold-listings/<suburb>-<state>-<postcode>/` or `…/?suburb=<suburb>-<state>-<postcode>,…`. A search for several suburbs uses the first. The page state is `{ status: 'browse', area }`.
- **The count** (`areaStats` in `background/comments.ts`): one query, `suburb ==`, served by the automatic single-field index, capped at 500 comments (shown as "500+" if reached), with postcodes checked in the extension (comments without one are counted). Cached for 10 minutes (`area:` keys, cleared by the user's own writes like the other comment caches).
- The privacy policy says the suburb of a search page is sent to count its comments.

## Tabs and the watchlist

The panel's tabs are a segmented control under the header: **Property** (property pages only, with the comment count), **Recent**, **Watchlist** and **Search**, each with an icon. When the panel is narrower than 460px (a CSS container query on `.panel`), the labels are visually hidden and only the icons show. **The header follows the selected tab** (`headerFor`): its eyebrow names the tab with its icon (`TAB_HEADINGS`), so it's named even when the tabs show only icons, and the title and subtitle describe it: the property's address and locality (with the Watch star, Property tab only), "Latest comments", "Your watchlist" with how many properties and new comments, or "Search comments". Subtitles are kept to one short line so the header's height, and the list below, don't jump between tabs.

**Watchlist** (`shared/watchlist.ts`, `ui/Watchlist.tsx`): users watch a property with the ☆ button in the panel header (property pages) or on a search result's detail view, up to `MAX_WATCHED` (25). Entries (`WatchedProperty`) hold the address fields, display strings and `seenAt`, the newest comment the user has seen; one entry per property (`watchKey`: canonical address, suburb, postcode).

- **Stored in `storage.sync`**, so it follows the user across devices when their browser syncs extension data, falling back to `storage.local` if sync is unavailable or full (8 KB per item, which 25 entries stay well under). Changes are read-modify-write and other tabs update through `storage.onChanged`. Nothing is sent to Firestore.
- **New comments:** while the panel is open, each watched property's comments are looked up with `listComments` (through the cache, so reopening is cheap; the URL is rebuilt as the realestate.com.au profile page, since entries added from Search have no listing). Comments by others newer than `seenAt` count as new: shown per property and as a count on the Watchlist tab. Opening a watched property in the tab, or viewing its own page, marks them seen. There's no background polling and no notifications (which would need the `notifications` permission).
- Watched properties can be opened in the tab to read, vote on and report comments, like search results; commenting still needs the property's page.

## Linking to a property (`propertyLinks` in `shared/property.ts`)

Wherever the panel shows a property other than the current page (Recent, Search), it links to the property's **profile pages on both sites, built from the stored address**, plus a Google search for the address. It never links to the listing the comment was posted on: realestate.com.au deletes a listing's page once the property is rented or sold, so stored listing URLs go dead. Profile pages exist for essentially every address whether or not it's listed, show its history, link to any current listing, and the extension shows the comments there.

- realestate.com.au: `/property/<abbreviated address>-<suburb>-<state>-<postcode>/`, units prefixed `unit-`: `/property/unit-41-10-14-hazlewood-pl-epping-nsw-2121/`
- domain.com.au: `/property-profile/<address, street type spelled out>-<suburb>-<state>-<postcode>`

In Recent they sit with the comment's actions, next to Report. The site the user is on is listed first. The Google link is the fallback for the rare address neither site has a page for (brand-new builds, lots, off-the-plan units); the comments themselves are never lost either way, since they're keyed by address and always reachable from Search. Checked on 2026-10-11 by opening both profile links for all 19 stored properties with `pnpm live-check`: 36 of 38 opened the right page. The two misses are the same unit, 6/21-25 Truganini Road, Carnegie: **street-number ranges are inconsistent** (domain.com.au lists it as 6/25, realestate.com.au under none of 6/21-25, 6/21 or 6/25), and that can't be predicted without fetching, so ranges just rely on the Search link. The links render as small buttons (`.property-links`) but stay `<a>` elements, since they navigate.

The `url` field is still written on new comments (the field set is fixed by the security rules) but is no longer displayed. **Existing comments don't need migrating**: links are derived from `address`/`suburb`/`state`/`postcode` at display time.

Posting doesn't depend on profile pages. A comment can be left on any page the extension can identify (listing, sold listing or profile, on either site), and it's stored by address, so a rental listing whose property has no profile page works exactly the same.

## Replies and editing

**Replies are one level deep, like Discord.** A reply is a normal `listingcomments` document with `parentId` (the top-level comment) and `replyToId` (what it answers: the parent, or another reply in the thread). Replying to a reply adds to the same thread, and the new reply shows "↪ Name: start of their comment" above it (`replyContext`; clicking it scrolls to that reply). Nested trees were ruled out: indentation doesn't fit a narrow panel or phones, and deleting a middle comment would orphan its branch.

- **Same collection, on purpose.** A reply copies its parent's stored `address` (which may be an older spelling) and `suburb`, so the property's existing query returns replies with no extra read or index, and the rules can check it belongs to the same property. Old releases (2.0.0) don't know `parentId` and show replies as ordinary comments; that's accepted as temporary.
- **Display** (`buildThreads`): top-level comments follow the chosen sort, replies sit under them oldest first, indented with a line down the side (less on phones). A reply whose first comment was deleted becomes its own thread, marked "Replying to a deleted comment". Recent shows replies flat with a "Reply" chip. Counts (launcher, tab) include replies.
- **Posting:** Reply on a comment (property tab only, since posting needs a page-confirmed property) puts a "Replying to …" bar above the composer; Esc or ✕ cancels. The background (`replyFields`) reads the target to find the parent and checks it's on this property. Replies count towards the hourly rate limit but not the per-property daily one.

**Editing:** the poster can edit a comment for `EDIT_WINDOW_MS` (15 minutes) after posting, inline, with the same Write/Preview box (and the posting rules first, if the user hasn't agreed to them yet). Only comments with `authorAuthUid` (like delete), enforced by the rules with the same window. Edited comments show "(edited)" with the time on hover. The Edit button disappears when the window closes (`useEditable`).

**Write/Preview** (`MarkdownEditor`): the composer and the edit form have GitHub-style tabs. Preview renders with the same code as posted comments, plus extra-small image thumbnails, so it shows exactly what will appear. The text box stays in the page (hidden) while previewing, and the preview takes exactly the text box's height (scrolling if its content is longer) so switching tabs never makes the panel jump. After posting, the composer goes back to Write (`resetKey`).

**Publish the rules before releasing:** the extension's replies and edits are refused until the updated `firestore.rules` is live. The new rules still accept everything older versions send.

## Address search (`shared/search.ts`, `searchComments` in `background/comments.ts`)

The panel's **Search** tab (on every page) finds properties that already have comments, without opening a listing. A ✕ in the box (our own; the browser's search-cancel button is hidden, since only Chrome has one) or Esc clears the query; Esc with an empty box closes the panel as usual. It accepts a full or partial address, a street on its own, a suburb or a postcode ("46 Stanley Road, Epping", "Stanley Rd", "Epping", "2121"). Firestore has no fuzzy or full-text search, so it works in two steps:

1. **Firestore fetches candidates** using whatever the query gives it (`parseSearchQuery` → `searchLookups`), each served by an automatic single-field index, so no composite index is needed (all checked against production):
   - **Street number** (the query starts with one, after `canonicalAddress`, so "Unit 41, 10-14 Hazlewood Pl" starts "41/10-14"): `address` prefix range. Used alone, since it's already precise.
   - Otherwise **postcode** (`postcode ==`) and **suburb**: `suburb` prefix range for the last one, two and three typed words, since the query may be "Stanley Road, Epping" or "North Strathfield".
   - **Fallback**: if nothing scores well enough, the 500 most recent comments (`ORDER BY createdAt DESC`) are scanned instead. That covers a street on its own and misspelt suburbs ("Concrd").

   Prefix ranges are `field >= prefix AND field < prefix + PREFIX_END`, where `PREFIX_END` is U+F8FF (the usual Firestore prefix bound; written as `String.fromCharCode(0xf8ff)` because an invisible literal character in source is a trap). Each lookup is cached for 60 s, since users type one character at a time, and the cache is cleared on any write.

2. **The extension ranks the candidates.** Comments are grouped by property (canonical address + suburb + postcode, so legacy spellings like `97  yates ave` join their property). `scoreMatch` compares each query word other than the street number (street name, type, suburb) with the property's words using prefix matching ("stan" → "stanley") and Damerau-Levenshtein similarity (typos, swapped letters), with street types expanded on both sides ("rd" = "road"). Every word must score ≥ `MIN_WORD_SCORE` (so a wrong suburb or street rules a property out) and the average must reach `MIN_SCORE`. A typed postcode or state must match exactly. Up to 20 results, best match first, then most recently commented.

Limitations: a street number, when given, must be exact (searching "10-14 Hazlewood Place" won't find unit "41/10-14"). A street-only search or misspelt suburb only reaches the 500 most recent comments. Each result links to the property's profile pages (see "Linking to a property"). Search results can be upvoted and deleted (own comments) like anywhere else, but not commented on: posting needs a page-confirmed property.

Scaling: street-number, postcode and suburb lookups stay small as comments grow, since each reads only matching comments. The recent-comments fallback is the part that degrades (it costs up to 500 reads and covers less of the data over time). A dedicated search index (e.g. a `properties` collection with a street-name field, or an external search service) would be the next step; both need backend changes.

## Images in comments (`shared/images.ts`, `ui/Images.tsx`)

Comments can't embed images, but a link to an image on a supported host is shown as a thumbnail under the comment's text; clicking one opens a lightbox over the whole window (arrow keys between a comment's images, Esc or the backdrop closes it, "Open original" opens the link as posted). In the lightbox you can zoom with a pinch, a double-tap or double-click (to 2.5×, again to reset) or the scroll wheel (1–4×), drag the image when zoomed (kept covering its frame), and on touch screens swipe sideways for the next or previous image or down to close (`useZoom` in `Images.tsx`; the maths, tested, in `content/zoom.ts`). The image has `touch-action: none` so the browser doesn't zoom the page instead; swiping is touch-only so mouse drags don't change images by accident. Tested with Playwright (mouse) and CDP touch events in Chromium, not on a real phone. There's no upload: images stay on the host the poster chose, and we never host anything.

- **Which links:** every link that survives sanitizing, whether written `[text](url)`, as a bare URL, or as markdown image syntax `![alt](url)` (rendered as a link with the alt text, never as `<img>` in the text). URLs inside `code` don't count. At most `MAX_COMMENT_IMAGES` (4) per comment, without repeats. The link text, unless it's the URL, is the caption.
- **Allow-listed hosts only** (`DIRECT_HOSTS`: Imgur, ImgBB, Postimages, Flickr, Gyazo, imgbox, Reddit), and only URLs ending in an image file type, loaded over HTTPS without the query string. Every reader's browser loads these images, so an arbitrary URL would let a poster log readers' IP addresses (a tracking pixel) or show content from an unmoderated server. Adding a host: it must serve images directly at stable URLs; not Discord (links expire) or Google Drive/Photos (no direct URLs). Update `IMAGE_HOST_NAMES` (shown in the formatting help) and `tests/images.test.ts`.
- **Imgur page links** (`imgur.com/<id>`) and bare `i.imgur.com/<id>` become `i.imgur.com/<id>.jpg`; Imgur serves the image whatever its real type. An ID needs a digit or capital, so site pages like `imgur.com/upload` aren't mistaken for images. **Albums and galleries** (`imgur.com/a/…`, `/gallery/…`) and the other hosts' page links (`ibb.co/…`, `postimg.cc/…`) stay plain links: finding their images needs the host's API or fetching the page, which would need host permissions. `.gifv`/`.mp4` are videos and aren't shown.
- Images load with `referrerpolicy="no-referrer"` and `loading="lazy"`. A thumbnail that fails to load (deleted image, host blocked in the reader's country) is dropped; its link is still in the text.
- **Site CSP:** the images are loaded by the page, so a site `img-src` policy could block them. Checked on 2026-10-12 with a CDP probe in the extension's content-script world: realestate.com.au's CSP has no `img-src` or `default-src`, domain.com.au sends none, and an Imgur image loaded on both. If either adds one, thumbnails just disappear; showing them would then need fetching through the background (new host permissions).
- The lightbox is portalled to the top of the shadow root (outside `.panel`, which is `overflow: hidden`), so it's still inside the host for click-outside. It's dark in both themes (`--lightbox-*` tokens).
- The privacy policy says image hosts see readers' IP addresses. The e2e test doesn't cover images (no production comment has one); they were checked manually in a test page with stubbed image requests.

## Reports, complaints and legal pages

Comments are anonymous, so complaints about them come to the maintainer, who is the publisher in Australian defamation law (_Fairfax v Voller_). The 2024 defamation reforms give hosts a defence if there's an accessible complaints mechanism and complaints are dealt with promptly (removal within 7 days); the browser stores also require a way to report user content. So:

- **Report** on every comment that isn't the user's own opens `ReportDialog`: a reason (`REPORT_REASONS`), optional details, and the complaints email for legal complaints. It's sent through the background (`reportComment`) to the private `reports` collection; the security rules let users create reports but never read them, and allow one report per person per comment (a repeat is refused, shown as "You may have reported this comment already"). Nothing is hidden automatically: the maintainer reviews reports with `pnpm moderate` (see "Moderating reports"). 2.0.0 opened a public GitHub issue instead; those releases keep doing so until users update. Reason IDs are stored, so never rename or remove one; `tests/reports.test.ts` checks the list matches the rules.
- **Complaints** in the footer is a `mailto:` to `COMPLAINTS_EMAIL` (`report.ts`).
- **Terms** and **Privacy** in the footer open the terms of use and privacy policy (`Legal.tsx`) in a `Dialog`. They describe what the extension actually stores and sends: **when you change what's collected or stored (Firestore fields, `storage.local` keys, services), update the privacy policy and its date.** Neither has been reviewed by a lawyer.
- **Posting rules** (`POSTING_RULES` in `Legal.tsx`, `PostingRulesDialog`) are shown in a dialog before the user's **first** post, reply or edit, and repeated in the terms. Agreeing stores `postingRulesAccepted` = `POSTING_RULES_VERSION`; cancelling doesn't count. **Bump `POSTING_RULES_VERSION` when the rules change in substance**, so everyone agrees to the new ones before their next post. (Until 2026-10-12 they were shown before every post, which users found annoying.) They keep comments to the property, the building and the area (someone else’s experience is fine if it’s said to be) and away from identifiable people. Bad experiences are explicitly welcome; the rules steer them towards describing what happened rather than labelling or accusing people.

### Moderating reports (`pnpm moderate`)

`scripts/moderate.ts` starts a server on `127.0.0.1` (random port) and opens `moderate.html` in the browser. The page lists reported comments grouped by comment, oldest open report first (with a warning once it's 3+ days old, given the 7-day target), showing the comment's text, author, property links and every report. Actions: **Remove comment**, **Remove and ban poster** (adds a `bannedUsers` document with the comment's `uid`), **Dismiss reports**; each closes all the comment's open reports. A Resolved view shows past outcomes.

- **Credentials:** the Firebase Admin SDK (`firebase-admin`, a dev dependency, never bundled) with a service account key, whose path is `FIREBASE_SERVICE_ACCOUNT` in `.env` (see `.env.example`). Create it in the Firebase console → Project settings → Service accounts → Generate new private key, and keep it outside the repo. The Admin SDK bypasses the security rules, which is why reports can stay unreadable to everyone else. It works on the free Spark plan.
- **Local-only by design:** it listens on `127.0.0.1` only, refuses requests with any other `Host` (DNS rebinding), and every API call needs a random per-run token, passed in the URL hash (never sent to the server or logged). The page shows everything from the database with `textContent`, since reports are written by anyone.
- **No notifications:** nothing tells the maintainer a report arrived; run it every few days. A scheduled job (e.g. a GitHub Action in a private repo holding the key) could check and notify, but doesn't exist yet.
- No automated test runs it against production; its access checks were tested manually with a fake key, and the page with fake data.

## Extension storage (`storage.local`)

Listed in `StoredData`. One key predates 2.0 and **must keep its name**:

- `CTextFilterStore_strCleanPattern_1039531631`: the user's anonymous ID (UUID). Losing it means their comments stop showing as theirs ("You") and their votes stop being recognised.

`tos_accepted` (1.x to 2.0.x) is no longer read: it recorded agreement to older terms, and the current posting rules are tracked by `postingRulesAccepted` instead. Old installs still have it; it's harmless.

`storage.sync` holds one key, `watchlist` (see "Tabs and the watchlist"; in `storage.local` if sync isn't available).

Others: `displayName`, `panelOpen`, `panelWidth`, `sort`, `theme` (`light`/`dark`/`system`), `postingRulesAccepted` (the rules version agreed to), `postHistory` (rate limiting). 1.x also wrote some keys into the _site's_ `localStorage` (`comments-panel-*`); 2.0 doesn't use them.

Deleting depends instead on the Firebase Auth session, which the Auth SDK keeps in the extension's IndexedDB (`indexedDBLocalPersistence`, the web-extension build's default), not in `storage.local`. It survives browser restarts; reinstalling the extension loses it, and with it the ability to delete earlier comments.

## Security model and known gaps

Everything client-side is a courtesy, not a control: the rate limit (5 posts/hour, 3 per property per day; replies count towards the hourly limit only), the ownership check before deleting, the ban check and comment validation all run in the extension, and anyone can call Firestore directly with the public config. **Real enforcement must be in the Firestore security rules.**

**`firestore.rules` is a copy of the deployed rules**, published by hand in the Firebase console (Firestore Database → Rules); the console is the source of truth, so publish any change there and keep the file in sync. Until 2026-10-11, any signed-in (i.e. anonymous) user could edit or delete any comment, and create bans. Now:

- `listingcomments`: read when signed in; create only with the extension's field set (`hasOnly`) and length limits, and `authorAuthUid` (if present) must be the caller's; a reply (`parentId` and `replyToId`, both or neither) only under an existing top-level comment with the same stored `address` and `suburb`; update only a single vote (`votes` ±1, one `userVotes` key), or an edit: by the poster (`authorAuthUid`), only `text` (5–1200 chars) and `editedAt` = server time, within 15 minutes of `createdAt`; **delete only when `authorAuthUid` is the caller's Firebase Auth UID**. `uid` can't be used for this: it's client-generated and visible to everyone. So comments without `authorAuthUid` (2.0.0 and 1.x) can only be deleted by the maintainer in the console; the extension shows Delete only when `canDelete` (`CommentView`), and the background checks it again before deleting. (From 2026-10-11 until this rule was published, delete was `if false`.)
- `bannedUsers`: read when signed in; no writes. `comments` (pre-1.x-refactor collection, unused): locked.
- `reports`: create only, when signed in, with exactly the report fields, a known reason, details ≤ 1000 chars, `reporterAuthUid` = the caller, `createdAt` = server time, the ID `<commentId>_<caller's Auth UID>`, and an existing comment. No reads, updates or deletes (so a second report from the same person fails as an update). Only the Admin SDK (`pnpm moderate`) reads them. **Publish these rules before releasing a version with the Report dialog**, or every report fails.
- **`pnpm test:rules`** runs `tests/rules/firestore.test.ts` against the local Firestore emulator (Java needed; firebase-tools downloads the emulator on first run): creates, replies, votes, edits, deletes and reports, allowed and refused. Run it before publishing any rules change. `scripts/test-rules.ts` starts and stops the emulator itself, because `firebase emulators:exec` leaves the emulator's Java process running on Windows.
- Checked after publishing with writes carrying an impossible `updateTime` precondition: Firestore evaluates rules before preconditions on existing documents, so `PERMISSION_DENIED` vs `FAILED_PRECONDITION` shows what the rules allow without changing data. Creates can't be checked this way (on a new document the precondition is checked first), so test posting with the extension.

Still to do:

- The rules can't stop one person voting many times with different `userVotes` keys, or voting on their own comment, since votes are keyed by the unverifiable `uid`. Keying them by Auth UID would fix it but would forget everyone's existing votes.
- Enforce bans in the rules rather than in the client (ban documents have random IDs, so this needs them keyed by user ID).
- **Enable Firebase App Check** so Firestore only accepts requests from the genuine extension. Client-side limits (the refresh interval, rate limits) can be bypassed by calling Firestore directly with the public config. The project is on the free Spark plan, so there's no billing and no budget alert to set: abuse can't cost money, but once the daily free quota is used up Firestore refuses requests until it resets, and the extension stops working until then.

Comment rendering is safe by construction: markdown goes through DOMPurify with a small allow-list (no `<img>`; image thumbnails are separate `<img>` elements built only from allow-listed hosts, see "Images in comments"), links get `rel="noopener noreferrer nofollow ugc"`, and nothing is assigned to `innerHTML`.

## Build, run, test

Requires Node ≥ 22.18 (runs the TypeScript scripts natively; CI uses 24) and pnpm.

```sh
pnpm install
pnpm build          # → dist/chrome, dist/firefox (gitignored)
pnpm dev            # rebuild on change, with inline source maps
pnpm test           # unit tests (Vitest)
pnpm test:rules     # firestore.rules against the Firestore emulator (needs Java; not part of check)
pnpm typecheck      # tsc --noEmit
pnpm lint           # ESLint (typescript-eslint, type-aware)
pnpm format         # Prettier
pnpm check          # all of the above + build; what CI runs
pnpm e2e            # browser smoke test against dist/chrome, on fake pages (see below)
pnpm live-check     # the built extension on the real sites (see "Checking the live sites")
pnpm moderate       # review reported comments (needs FIREBASE_SERVICE_ACCOUNT, see "Moderating reports")
pnpm lint:firefox   # web-ext lint (AMO's validator) on dist/firefox
pnpm sign           # signed Firefox .xpi for testing; uploads to AMO and uses up a version (see below)
```

**Loading locally** (day-to-day testing uses `dist/chrome` loaded unpacked, hence rebuilding after changes):

- **Chrome:** `chrome://extensions` → Developer mode → Load unpacked → `dist/chrome`. Reload after each build.
- **Firefox:** `about:debugging#/runtime/this-firefox` → Load Temporary Add-on → `dist/firefox/manifest.json`. Removed when Firefox restarts.
- **After reloading the extension, refresh the site's tabs.** The old content script is orphaned.
- Logs: page console (filter `[Real Estate Comments]`; page state changes are logged at debug level) and the background console (Chrome: "service worker" link on the extensions page; Firefox: Inspect).

**`pnpm e2e`** (first run: `pnpm exec playwright install chromium`) loads `dist/chrome` into Chromium and serves fake pages at real listing URLs, because the real sites block automated browsers. The extension runs for real, including Firebase sign-in and **reads from production**. It never posts, votes or deletes; keep it that way. It checks: comment count badge, panel, a 1.x irregular key (`97  yates ave`), domain.com.au, stale titles after `pushState`, the posting rules prompt before a first post, Write/Preview, starting and cancelling a reply (never posted), the report dialog (opened and closed, never sent), watching and unwatching a property (storage only), the suburb card on a search page (Concord NSW 2137), the sort/filter dropdowns (With photos, and the search results' options), the terms/privacy dialogs and complaints link, recent comments, and a phone-sized viewport. It relies on a few production comments existing (listed in the script); if one is deleted, pick another property. `--screenshots <dir>` saves light and dark screenshots of each step. It doesn't cover Firefox or the real sites' markup; `pnpm live-check` covers the real sites.

**Before considering a change done**, run `pnpm check`. For UI or page-detection changes, also run `pnpm e2e` (look at the screenshots) and `pnpm live-check`. For any change to `firestore.rules`, run `pnpm test:rules` and add cases to `tests/rules/firestore.test.ts` before publishing it. Note what wasn't tested: usually Firefox, and posting, voting and deleting, which no automated check does against production.

### Signed Firefox build (`pnpm sign`)

`pnpm sign` gets a permanently installable, Mozilla-signed `.xpi` for testing in Firefox (temporary add-ons from `about:debugging` disappear on restart). It bumps the patch version in `package.json` (`scripts/bump-version.ts`), builds, and submits `dist/firefox` to Firefox Add-ons as **unlisted** (signed for self-distribution, not published), saving the `.xpi` to `web-ext-artifacts/`. Install it from `about:addons` → gear → "Install Add-on From File".

- **Credentials:** `WEB_EXT_API_KEY` / `WEB_EXT_API_SECRET` in `.env` (git-ignored; see `.env.example`), from https://addons.mozilla.org/developers/addon/api/key/.
- **Don't run it casually.** It uploads to AMO and changes the version.
- **Version numbers are spent:** AMO never accepts the same version twice for an add-on, listed or unlisted, and this add-on is also listed publicly under the same ID. Every `pnpm sign` uses up a patch version, so the next public release must use a higher version than the last signed one, or AMO rejects it. The release workflow takes its version as an input, so pick one above the latest signed build.

`pnpm lint:firefox` (also the last step of `pnpm check`) runs `web-ext lint`, AMO's own validator, on `dist/firefox`. It must stay at 0 errors. Known warnings: `MISSING_DATA_COLLECTION_PERMISSIONS` (the declaration is disabled for now, see below) and two `UNSAFE_VAR_ASSIGNMENT`s for `innerHTML` inside bundled libraries (Preact's `dangerouslySetInnerHTML` support, which we don't use, and DOMPurify's parser), which are expected.

**Firefox data collection declaration (prepared, disabled):** Firefox shows the data types declared in `browser_specific_settings.gecko.data_collection_permissions` in the install prompt, and users must accept required ones to install. It's mandatory for new extensions since November 2025; Mozilla said existing ones would follow "in the first half of 2026" with notice on the add-ons blog, but as of 2026-10-12 hasn't announced a date. When it's enforced, AMO refuses to sign versions without it, so it's needed before the next release after that. It's written in `src/manifest.ts` but commented out, because: **on update, Firefox prompts existing users to approve every newly added required type** (`none` never prompts), and **once a version declares it, every later version must**. Don't enable it early, and don't `pnpm sign` a build with it unless you mean to keep it. The chosen types, as **required**: `browsingActivity` (viewing a listing sends its address to look up comments, even without posting; Mozilla counts any data leaving the browser, anonymous or not, so `none` would be wrong) and `personalCommunications` (posted comments and names). Not `websiteContent`: the address read from the page is the same information as `browsingActivity`. To enable: uncomment it and `gecko_android`, set `strict_min_version` to 140 (the key needs Firefox 140 desktop / 142 Android; `web-ext lint` warns otherwise) and the Firefox target in `scripts/build.ts` to `firefox140`, and add a CHANGELOG line. After that, add a type only when a change really starts sending a new kind of data, and update the privacy policy with it.

## Releasing

`.github/workflows/build-and-release.yml` runs manually with a `version` input. It sets `package.json`'s version (the manifests read it at build time), runs `pnpm check`, zips `dist/chrome` and `dist/firefox`, makes a source zip (Firefox Add-ons asks for source code of bundled extensions), commits the version bump to the branch, and creates a GitHub release `v<version>` with `CHANGELOG.md` as the body.

`CHANGELOG.md` holds only the entries for the upcoming release, as a flat bullet list in plain user-facing language. Append to it; don't rewrite existing entries. Store uploads (Chrome Web Store, Firefox Add-ons) are manual.

`ci.yml` runs `pnpm check` on pushes to `main` and on pull requests.

## Conventions

- **TypeScript, strict.** No `any`; validate anything crossing the message boundary at runtime.
- **Style:** Prettier config in `prettier.config.js` (2 spaces, no semicolons, single quotes, 120 columns, sorted imports). Short `//` comments explain _why_, above the code they describe. No JSDoc blocks.
- **UI:** Preact function components and hooks, plain CSS in `styles.css`. **Colours are only ever tokens** defined on `:host` as `light-dark(<light>, <dark>)` (neutrals: in light mode white, with a cool blue-white `--surface-muted` and cool grey borders; and the extension's blue as the only accent: `--accent`, the launcher's colour since 1.x; the launcher keeps the filled chat-bubble `BrandIcon`); never hard-code a colour in a rule. The theme follows the system until the user picks one with the header's sun/moon button (`theme` in storage), which sets `data-theme` on the host and with it `color-scheme`. `light-dark()` is why the minimum versions are Chrome 123 / Firefox 128 (Firefox goes to 140 when the data collection declaration is enabled; see "Signed Firefox build"). Dialogs over the panel use the `Dialog` component (`.overlay` backdrop, absolutely positioned inside `.panel`, + `.dialog`), which closes on backdrop click and Esc and stops Esc from also closing the panel; render it inside `.panel`. While the panel is open, a slight dark `.page-backdrop` covers the page; clicking it, or anywhere outside the panel, closes the panel (the backdrop handles its own clicks; a capture-phase `pointerdown` listener in `App`, checked with `composedPath()` against the shadow host, catches anything else). The panel opens at its maximum width (`MAX_WIDTH`, capped to the window) until the user drags its edge; after that their width (`panelWidth`) is used. Icons are inline Lucide paths in `icons.tsx`. **Pressing a control must never start a text selection on the page**: buttons, the launcher and the backdrop have `user-select: none`, and the launcher and backdrop also `preventDefault()` on `mousedown`. In Firefox, pressing a control that then disappears (the launcher, when the panel opens) left a selection drag pending, and the next click (on the backdrop, over page text) completed it, selecting a large part of the page. Automated input (Playwright in Chromium and Firefox, CDP in real Chrome) doesn't reproduce this; only real mouse input in Firefox does, so check changes here by hand in Firefox (the fix was confirmed that way on 2026-10-11). Never use `alert`/`confirm` (they block the page and the browser); show messages inline. Keep it keyboard accessible (Esc closes the panel, visible focus).
- **User-facing text:** plain Australian English, sentence case, curly apostrophes (’) in UI strings.
- **Permissions:** `storage` (local, session and sync) plus host permissions for the two sites (`SITE_MATCHES` in `shared/sites.ts`). Keep them minimal: every permission needs justifying in store review, and adding one prompts existing users on update. Firestore and Auth endpoints don't need host permissions (they allow CORS).
- **Manifests:** edit `src/manifest.ts` only. Chrome uses `background.service_worker`; Firefox uses `background.scripts` (event page) and must keep `browser_specific_settings.gecko.id = real-estate-comments@zevnda.com`.
- **Bundles are not minified** so store reviewers can read them.
- **TypeScript version:** pinned to 6.0 because typescript-eslint doesn't support 7.x yet.
- **Line endings:** LF everywhere, enforced by `.gitattributes` (`* text=auto eol=lf`). Without it, `core.autocrlf=true` on Windows checked files out as CRLF and Prettier flagged every file.
